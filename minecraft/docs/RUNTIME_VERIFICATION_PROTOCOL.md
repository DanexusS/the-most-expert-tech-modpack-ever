# Runtime verification protocol

Этот протокол используется только после полного статического `PASS`. Он проверяет то, что невозможно достоверно доказать анализом файлов: запуск клиента, фактическую регистрацию предметов и рецептов, загрузку FTB Quests, переключение языка и сохранение мира.

## 1. Подготовка теста

Перед запуском зафиксируйте:

- точный 40-символьный commit ветки;
- дату и время с часовым поясом;
- версию Java;
- выделенную память;
- краткое описание CPU/GPU/ОС;
- название отдельного тестового мира;
- название экземпляра лаунчера или сервера.

Используйте чистый экземпляр сборки без старых `logs`, `crash-reports`, `kubejs/exported` и тестового мира. Не используйте `/reload` для проверки startup-скриптов: требуется полный запуск.

Ссылки в `evidence` могут указывать на:

- относительный путь к сохранённому логу;
- имя и временной диапазон видеозаписи;
- файл с командами и их выводом;
- таблицу проверки рецептов;
- скриншот или экспорт FTB Quests;
- отчёт профайлера.

Доказательство должно позволять другому тестировщику понять, что было проверено, на каком commit и с каким результатом.

## 2. Обязательные gate

### `clean_client_start`

1. Удалите или архивируйте старый `latest.log`.
2. Запустите клиент полностью.
3. Дождитесь главного меню.
4. Проверьте отсутствие startup-ошибок KubeJS, ошибок регистрации предметов и аварийного завершения.
5. Сохраните лог и отметьте покрытие `1/1`.

### `new_world_create_save_reopen`

1. Создайте отдельный тестовый мир.
2. Дождитесь полной загрузки игрока и чанка.
3. Сохраните и выйдите в меню.
4. Повторно откройте тот же мир.
5. Проверьте отсутствие ошибок чтения мира, квестов и KubeJS-данных.
6. Сохраните лог и отметьте покрытие `1/1`.

### `kubejs_milestone_items_exist`

Проверьте все **18** milestone-предметов из `config/expert_progression_contract.json`:

- предмет существует в registry;
- отображается с корректным именем;
- может быть помещён в инвентарь тестовой командой или через тестовый рецепт;
- не превращается в missing item после сохранения и повторного открытия мира.

В evidence приложите таблицу из 18 строк. Покрытие должно быть `18/18`.

### `strategic_recipes_verified`

Для каждого из 18 макроэтапов выберите финальный milestone-рецепт:

1. Откройте рецепт в интерфейсе просмотра рецептов.
2. Проверьте соответствие текущему авторитетному рецепту.
3. Подготовьте входы в отдельном тестовом мире.
4. Создайте результат реальным способом, а не командой.
5. Проверьте расход входов, единственный выход и отсутствие параллельного упрощённого рецепта.

Покрытие должно быть `18/18`. Для машинных или внешних путей укажите фактическую машину и условия процесса.

### `representative_quest_tasks_complete`

Проверьте три класса задач FTB Quests:

1. `item` — предмет корректно распознаётся и завершает задачу;
2. `checkmark` — ручная приёмка сохраняется после закрытия книги;
3. `kill` — нужная сущность и количество корректно засчитываются.

После выхода и повторного входа прогресс должен сохраниться. Покрытие `3/3`.

### `language_switch_verified`

1. Откройте несколько основных этапов, curated manual и переработанную legacy-главу на `en_us`.
2. Переключитесь на `ru_ru` без изменения файлов сборки.
3. Повторно откройте те же квесты.
4. Проверьте заголовки, многострочные описания, названия этапов и отсутствие необработанных ключей.

Покрытие `2/2`.

### `second_clean_restart_and_world_reopen`

Этот gate выполняется только после первого запуска и проверки мира:

1. Полностью закройте клиент или сервер.
2. Архивируйте лог первого цикла.
3. Выполните второй чистый запуск без изменения файлов.
4. Откройте тот же тестовый мир.
5. Проверьте предметы milestone, прогресс трёх квестовых задач и одну стратегическую машину.
6. Убедитесь, что не появилась новая блокирующая ошибка или missing registry entry.

Покрытие `1/1`.

## 3. Рекомендуемые измерения производительности

Они не заменяют семь обязательных gate, но позволяют выявить регрессии до выпуска:

- три запуска baseline и candidate для медианы startup/world-load;
- 30-минутный soak с показательными фабриками;
- TPS p05 и MSPT p95;
- два сопоставимых post-GC измерения heap;
- максимальная частота повторяющихся строк лога;
- число сущностей и block entities в загруженных производственных чанках.

Не ставьте optional gate в `verified`, если отсутствует соответствующее числовое измерение.

## 4. Заполнение evidence-файла

Файл: `config/v1_runtime_evidence.json`.

Для подтверждённого gate требуется:

- `verified: true`;
- `checked_at` в ISO-8601 с часовым поясом;
- `coverage.current >= coverage.required`;
- непустой массив `evidence`;
- общий `pack_commit`;
- общий `measured_at`;
- заполненные поля Java, памяти, оборудования, мира и экземпляра.

После изменения выполните:

```bash
python minecraft/tools/runtime_evidence_quality_gate.py
python minecraft/tools/v1_product_readiness.py
```

Первый инструмент проверяет структуру и отклоняет неподтверждённые заявления. Второй меняет классификацию только когда все семь обязательных gate действительно подтверждены.

## 5. Правило выпуска

- Статический `PASS` без runtime evidence: **V1 candidate — runtime evidence required**.
- Семь подтверждённых gate на одном commit: кандидат может быть рассмотрен как `v1`.
- Второй чистый запуск и повторное открытие мира являются обязательной частью evidence, а не последующей формальностью.
